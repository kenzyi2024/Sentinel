# Architecture

Sentinel is a layered Spring Boot application with a hand-built React console. This document maps
the components and explains how a single agent action becomes an evaluated, explainable event.

## High-level

```
 React console (live REST  ──▶ Spring Boot backend ──▶ H2 / PostgreSQL
 or bundled demo fixtures)         (the engine)
```

- **Live mode** — the frontend calls the REST API at `http://localhost:8080/api`.
- **Demo mode** — if the backend is unreachable, the frontend serves JSON fixtures that were
  generated by the backend's `export` profile (real engine output). This is what powers GitHub Pages.

## Backend package layout

| Package | Responsibility |
|---------|----------------|
| `domain` | Immutable domain model (records) and enums — `Agent`, `AgentAction`, `Event`, `RiskAssessment`, `Policy`, `SecurityReport`, … |
| `security` | Capability model, `PermissionModel`, `PermissionChecker`, `ResourceClassifier` |
| `detection` | `InjectionScanner` (+ `PatternInjectionScanner`), `AnomalyDetector` (+ `WelfordVariance`), `EscalationDetector`, `CommandAnalyzer` |
| `risk` | `RiskEngine` + seven `RiskScorer` implementations |
| `policy` | `PolicyEngine`, `PolicyService`, `DefaultPolicies`, `ResourceMatcher` |
| `evaluation` | `ActionEvaluator` (the pipeline), `DecisionResolver`, `ExplanationBuilder`, `EvaluationContext` |
| `simulation` | `AgentFactory`, `VirtualProject`, `ScenarioLibrary`, `SimulationEngine`, `RunService`, `AgentStateMachine` |
| `telemetry` / `report` | `EventService` (event store), `ReportService` |
| `persistence` / `repository` | JPA entities, mappers, Spring Data repositories |
| `api` / `api.dto` | REST controllers and DTOs |
| `config` / `exception` | Properties, CORS, OpenAPI, seeding, export; global error handling |

The layering is strict: `domain` depends on nothing; detection/risk/policy/security depend only on
`domain` (+ their config properties); `evaluation` orchestrates them; `simulation` drives evaluation
and persistence; `api` is a thin adapter over services.

## The evaluation pipeline

`ActionEvaluator.evaluate(EvaluationRequest)` runs, in order:

1. **Resource classification** — `ResourceClassifier` → `ResourceSensitivity` (PUBLIC…SECRET).
2. **Permission check** — `PermissionModel` computes required capabilities; `PermissionChecker`
   compares them to the agent's grant → `PermissionCheck`.
3. **Injection scan** — `InjectionScanner.scan()` over ingested content → `InjectionFinding[]`.
4. **Command analysis** — `CommandAnalyzer.analyze()` for shell commands → `CommandAnalysis`.
5. **Anomaly detection** — `AnomalyDetector.analyze(history, action)` → `AnomalyResult`.
6. **Escalation analysis** — `EscalationDetector.analyze(history, action)` → `EscalationSignal`.
7. **Policy evaluation** — `PolicyEngine.evaluate(...)` → `PolicyDecision` (strongest effect wins).
8. **Risk scoring** — `RiskEngine.assess(context)` sums the seven scorers → `RiskAssessment`.
9. **Decision** — `DecisionResolver.resolve(...)` → allow / block / require-approval.
10. **Explanation** — `ExplanationBuilder` produces the reason bullets and recommendations.
11. **Event** — an immutable `Event` is built, linked to its predecessor, and persisted.

Steps 1–7 run *before* risk so any scorer can read their results; the decision and explanation run
*after* risk. The evaluator holds no mutable state — the run history is passed in each call — so it
is thread-safe and directly unit-testable.

## Risk model

`RiskEngine` injects the full list of `RiskScorer` beans (Strategy pattern). Each returns an
optional `RiskFactor` with `contribution = round(signal ∈ [0,1] × weight)`. The engine sums the
contributions, clamps to [0, 100], and buckets into a band. Weights and band cut-points live in
`sentinel.risk.*` (`RiskModelProperties`), so the model is re-tunable without recompiling. Adding a
new dimension is purely additive: implement `RiskScorer`, annotate `@Component`, done.

## Data model & persistence

Runs and events are persisted with Spring Data JPA. To keep the schema small while preserving the
rich domain objects, each `EventEntity` stores the queried columns (run id, sequence, decision,
risk score, action type, timestamp) plus a JSON projection of the full `Event`; `RunEntity` stores
aggregate counters plus the full `SecurityReport` as JSON. This event-store pattern avoids a sprawl
of child tables and stays stable as the domain evolves. H2 (file-backed) is the default; a
`postgres` profile switches to PostgreSQL.

## Frontend

React + TypeScript + Vite with a hand-built design system (no UI framework). `createApi()` probes
`/api/health` and returns a live or demo client behind one interface. Views: Landing, Run Explorer
(execution graph + event stream + risk rail + investigation drawer), Scenario Lab, Policies, About.
The SVG risk gauge and execution graph are hand-drawn — no chart library.
